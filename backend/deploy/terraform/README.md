# Backend infra (Terraform)

Provisions everything `.github/workflows/backend-deploy.yml` needs: Artifact
Registry, a Workload Identity Federation pool/provider + deploy service
account (keyless GitHub Actions auth), a Cloud SQL for Postgres instance, the
three Secret Manager secrets the workflow reads, and the Cloud Run service
itself (seeded with a placeholder image — real deploys happen via CI, not
Terraform).

This creates **billable GCP resources** (Cloud Run, Cloud SQL, Artifact
Registry). Run it yourself; nothing here runs automatically in CI.

## One-time setup

```bash
cd backend/deploy/terraform
gcloud auth application-default login   # or set GOOGLE_APPLICATION_CREDENTIALS

cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars: project_id, github_repo (org/repo), region

terraform init
terraform plan
terraform apply
```

Then copy the outputs into GitHub Actions secrets (Settings > Secrets and
variables > Actions):

| GitHub secret                  | Terraform output               |
|---------------------------------|---------------------------------|
| `GCP_PROJECT_ID`                | `project_id` you set             |
| `GCP_REGION`                    | `region` you set                 |
| `GCP_WORKLOAD_IDENTITY_PROVIDER`| `workload_identity_provider`     |
| `GCP_SERVICE_ACCOUNT`           | `deploy_service_account_email`   |
| `GCP_CLOUDSQL_CONNECTION_NAME`  | `cloudsql_connection_name`       |
| `DB_NAME`                       | the `db_name` you set (default `varianty`) |

```bash
terraform output
```

After that, push to `main` — `backend-deploy.yml` builds the image and
deploys it onto the Cloud Run service Terraform created.

## Notes

- DB and JWT secrets are generated by Terraform (`random_password`) and
  stored only in Secret Manager — they never appear in `.tf` files, state
  diffs shown here, or GitHub secrets.
- State is local by default (gitignored). For a team setup, create a GCS
  bucket by hand once and uncomment the `backend "gcs"` block in `main.tf`.
- `google_sql_database_instance` has `deletion_protection = true` by default
  (`cloudsql_deletion_protection` variable) — `terraform destroy` will refuse
  to drop the database unless you flip that first.
- The Cloud Run container image is excluded from Terraform's management
  (`lifecycle.ignore_changes`) on purpose, so re-running `terraform apply`
  never rolls back whatever image CI most recently deployed.
